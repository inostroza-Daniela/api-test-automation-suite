¿Qué es?

Las aplicaciones que usamos todos los días, como la del banco, la de delivery o una red social, piden información a un servidor: «muéstrame mis pedidos», «inicia mi sesión». A esa conexión se le llama API.

Este proyecto es un programa que hace esas mismas peticiones de forma automática, en 80 situaciones distintas, y revisa que cada respuesta sea la correcta.

¿Para qué sirve?

  • Encontrar errores antes que los usuarios. Si algo falla, se sabe antes de que llegue a las personas.
  • Ahorrar tiempo. Lo que a una persona le tomaría una tarde probando a mano, aquí toma 20 segundos.
  • Cambiar el código con confianza. Cada vez que alguien modifica algo, las pruebas corren solas y avisan si se rompió.

¿Qué encontró?

Al probar una API pública, encontró 4 errores reales. El más importante es de seguridad: en un sistema real permitiría modificar los datos de otra persona cambiando un solo número.

Los cuatro están en Defectos encontrados.

Una forma de verlo: es como el control de calidad de una fábrica, pero para software. Revisa cada pieza antes de que llegue al cliente, siempre con la misma lista y en segundos.

Detalle técnico

Qué verifica

La suite llama a los endpoints de DummyJSON como lo haría una aplicación real, con datos válidos e inválidos, y revisa cinco cosas en cada respuesta.

Código de estado

Que cada caso responda lo que corresponde.

404 si el usuario no existe

Contrato

Que los datos tengan la forma acordada.

schemas con Zod

Lógica

Paginación, ordenamiento, búsqueda y filtros.

limit=10 → 10 resultados

Errores

Que los datos inválidos se rechacen bien.

sin contraseña → 400

Seguridad

Tokens JWT, refresh y cookies seguras.

JWT alterado → rechazado

Defectos encontrados

Cada defecto quedó documentado con un test marcado con test.fail(): pasa mientras el defecto existe y avisa cuando la API lo corrige.

Endpoint Esperado Real
PUT /users/:id La respuesta describe al usuario de la ruta Un id en el body reemplaza el de la ruta
GET /auth/me 401 con un JWT de firma alterada 500 con el error interno de la librería JWT
POST /auth/login 400 con un expiresInMins fuera de rango 500
PATCH /posts/:id La respuesta mantiene todos los campos Falta el campo views

El primero es un caso de mass assignment (OWASP API Top 10). En un backend real, cambiar un número en el body permitiría modificar un registro distinto al de la URL, por ejemplo la cuenta de otra persona.

Cómo está construida

Arquitectura en capas: los tests describen qué probar y nunca conocen las URLs, así que un cambio en la API se corrige en un solo lugar.
